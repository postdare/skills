# Slow-Think

通过生成者与审查者分离，对已经存在的代码、方案或结论进行独立、对抗性的复核。

核心纪律：审查者只接收原始需求、最终产物和审查指令，不继承生成过程或主 agent 对产物的评价。

## 第一步：准备输入

确定以下两项：

1. 原始需求：用户真正想解决的问题、约束和验收条件。
2. 待审产物：需要复核的最终代码、方案或结论。

如果用户只提供了需求，先按需求产出结果，再将结果作为待审产物。

完成标准：原始需求和待审产物均已明确，可以原样交给审查者。

## 第二步：发起独立审查

派出一个不继承当前对话历史的 sub-agent。在支持 `fork_turns` 的环境中使用 `fork_turns="none"`。

审查任务的输入严格限定为：

1. `agents/reviewer.md` 的完整内容，作为审查任务指令。
2. 原始需求。
3. 待审产物。

完成标准：独立 sub-agent 已收到且仅收到上述三类输入。

如果环境无法创建独立上下文，在当前会话中仅依据原始需求和最终产物重新审查，并向用户明确说明这是隔离性较弱的降级审查。

## 第三步：校验审查报告

审查者必须遵守 `agents/reviewer.md` 中的检查清单、风险评级和输出契约。

收到报告后检查：

- 所有适用的检查项都有明确判断和依据；不适用项说明原因。
- 缺陷包含严重度、证据或触发条件以及修复建议。
- 风险评级与结论符合固定映射。
- 未验证项与缺失的关键验证已经列出。

完成标准：报告满足完整契约；存在缺项时，要求原审查者补充后再进入下一步。

## 第四步：按用户授权交付

- 用户只要求审查：原样呈现审查结论，不修改待审产物。
- 用户要求审查并修复：修复严重和中等缺陷，再对修订后的产物进行一次新的独立审查。
- 涉及不可逆操作或需要业务决策：呈现风险和选项，等待用户决定。

审查意见保持原始风险等级和严重度，主 agent 可以补充上下文，但不弱化审查者的判断。

完成标准：审查报告已交付；或者已完成用户授权的修订，并通过新一轮独立审查。
