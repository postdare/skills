# 图解

把关系画成可读的图：内容决定节点、方向和状态，手工构图决定位置、分组与走线。本文件是通用流程、格式与验收的唯一依据；已有项目的集成约定由项目适配技能提供。

## 1. 锁定目标与语义

先选分支：
- **新画**：从用户要求与提供的文档提取内容，记录来源；资料缺失会影响结论时先查已有资料，仍不明确则报告具体疑点。
- **修改**：读取目标图、对应内容和已有样式，只改变用户要求的部分；未要求改变的节点、边、文字、状态和含义保持原样。
- **批量**：先读 [references/batch.md](references/batch.md)，按其中的目标分配与主验收安排执行本流程。

列出目标集：每张图的稳定 `id`、来源、期望读出的关系、允许改动的文件/帧、输出目录和展示场景。已有仓库优先沿用其输出位置与集成入口；独立任务使用下面的 JSON 工具链。只修改目标集内的内容及明确列出的集成文件；共享渲染能力不足时报告缺口，单独获得改动范围后处理。

为每帧建立独立的 `content`：所有主要节点的 `id/label/value/status` 与所有边的 `from/to/label/kind`。它是**语义真值**，不能从排好的图反推，也不能为通过检查而删改。新增图的推导与编辑图的差异都须能对照来源。

**完成门槛**：目标集和改动范围明确；每个目标都有完整内容、来源与展示场景；影响语义的疑点已解决或明确阻塞该目标。

## 2. 选构图、写图稿

选择版式时读取 [references/layouts.md](references/layouts.md)，从 `assets/templates.js` 复制匹配关系的模板。模板只提供构图起点，文字、状态与关系仍以语义真值为准；复杂嵌套和内外循环沿用该参考中的组合方式。

消息按时间依次往返的关系（协议握手、请求/应答、重试）改用时序风格：声明 `diagram.lifelines` 生命线，消息用 `id@life:y` 锚在生命线上，自上而下即时间顺序；请求与返回按 UML 惯例用 `kind`（`flow` 实线实心 / `reply` 虚线开放箭头 / `async` 异步）区分。写法与规则见 [references/layouts.md](references/layouts.md) 的 Sequence style 一节和 [references/frame-format.md](references/frame-format.md)。

每帧写一句「主要关系 + 采用的构图」。相邻状态帧保持同一概念的位置与颜色稳定，让变化本身可见。

### 文档与图稿格式


独立输入为 `{title,frames:[{id,title,note?,content:{nodes,edges},diagram}]}`；画布默认 720×450，可设 `diagram.w/h`。写图稿前读取 [references/frame-format.md](references/frame-format.md)，按其中的完整示例与字段约定生成 JSON；已有项目按其适配技能写入。

### 构图基线

默认亮底、深色文字、圆角框，颜色按角色一致使用；可适配已有设计，并非固定品牌规范。内置 `mint/pink/violet/sky/amber` 有基础、`Soft`、`Pale` 三档，另有 `gray`。

- 以 720×450 为基线：四周留白至少 14；主要框高约 62–90，标签约 20px，副文字约 13px。长文字先合理换行/增宽；标签与状态角标各有独立空间。
- 主节点默认圆角矩形，可按语义选 `shape`：`diamond` 用于判断/分支，`ellipse` 用于起止，`pill` 用于状态标签。菱形与椭圆的可用区域是内接形状，尺寸要按 [references/frame-format.md](references/frame-format.md) 的内接规则预留，通常比同标签的矩形更大或需要更宽的画布。
- 主节点宜不超过 8 个；更复杂内容按可解释的子关系拆帧，并完整保留总语义。窄屏若仍须看全图，按实际显示尺寸决定是否拆图。
- 相邻框留约 60 的走线空间；同边多线用 `:0.3/:0.7` 错开，端点避开角标。曲线方向与出入边匹配，多节点环优先 `orbit`。
- 边标签用 `at` 手摆到线外，通常离线 3–30；线长至少容纳标签加两端留白，避免文字、框、标题和其他线相互遮挡。
- 容器先给标题留空间（可从 `titleY:17`、卡片从 `y+31` 开始），内部示意与外部主关系有清楚的视觉层级。

**完成门槛**：每个目标图稿完整；主要节点与边、标签、值、状态均对齐 `content`；示意元素与主语义分开；所有未请求的语义保持不变。

## 3. 生成与检查

`SKILL` 取本次加载的技能目录，`OUT` 取目标输出目录。技能资产/脚本按技能目录定位，输入和输出相对当前工作目录；从任何仓库都可运行，无需复制实现。

```bash
python3 "$SKILL/scripts/build.py" <document.json> --out "$OUT"
node "$SKILL/scripts/shoot.mjs" <preview-url> "$OUT"
python3 "$SKILL/scripts/sheet.py" "$OUT"
python3 "$SKILL/scripts/sheet.py" "$OUT" 390
```

构建生成 `$OUT/preview.html`。使用已有可访问服务，或用 Python HTTP 服务公开输出目录，自选可用端口，再传完整预览 URL。仓库适配任务可直接传其预览 URL。截图工具驱动本机无头 Chrome/Edge/Chromium（Node ≥ 22，无需额外安装；路径非标准时设 `BROWSER` 环境变量）；构建用 Python 3，审图表还需 Pillow。依赖不可用时报告具体缺项，不能把未截图称为已审图。

截图工具生成每帧 `<id>.svg`（自包含样式）、`<id>-1200.png`、`<id>-390.png` 及 `report.json`；拼图生成 `sheet.png` 与 `sheet-390.png`。两种宽度都会生成证据，验收重点按预定展示场景选择。

分开核对两类检查：
1. **几何**：`DiagramCheck.geometry(svg,diagram)` → `{errors,hints}`，检查文字/角标、框、线、标签、标题与边界的冲突；错误逐项修复，提示逐项判定。
2. **语义**：`DiagramCheck.semantic(diagram,content)` → `{errors,hints}`。独立模式严格核对节点与边的完整集合、空白/换行归一后的标签和值、`error/ok/warn/muted` 状态、边标签与阻塞类型；多余主节点/主边也是错误。容器标题映射为标签；内部小图与装饰不充当内容节点，不可把主要节点标成小图以绕过检查。
检查报错时读取 [references/troubleshooting.md](references/troubleshooting.md)，按缺陷修正构图；字段与渲染实现不靠试错猜测。

**完成门槛**：每个目标已渲染、JS 加载/运行无错；几何与语义错误分别为 0；每条提示都有保留理由或已修复；输出数量与目标集逐项对应。

## 4. 亲自审图并交付

打开最后一次修改之后生成的审图表，并检查每个目标的截图；缩略图无法判断文字/交点时读单帧。对预定桌面和/或移动展示尺寸逐项核对：
- 第一眼能找到主线，所有箭头方向、循环回流、分支归属与分组边界清楚。
- 标签、值和状态可辨认；换行自然；无拥挤、遮挡、越界或误导性的视觉强调。
- 图意与来源一致；状态色/角标、阻塞边和示意层级表达准确。
- 同组图的颜色、尺寸和位置变化有理由；编辑图的未请求内容保持原意。

有问题就改图稿，再生成检查与最新截图。**几何 0 错误只说明没有检测到几何冲突，不能代替语义核对或视觉判断。**

**交付门槛**：目标集内全部图完成，最新证据已亲自看过，适用展示尺寸均通过；仓库集成入口已更新且相关回归通过。汇报提供完成数量、内容/图稿与预览路径、SVG 和审图表路径、几何/语义/JS 检查结果、逐帧视觉结论与剩余提示的理由。未解决的语义疑点、视觉问题或未执行项明示，不能计为通过。
