# Demo 输入：交付与运营图解

本文件是 demo 的内容来源。图稿中的节点、文案、方向和状态以此为准；它不依赖课程数据或任何项目运行时。

## release-flow：发布流水线

四个阶段按顺序执行：代码提交 → 自动构建 → 变更验收 → 灰度上线。代码提交触发自动构建，第一条边标注「触发」。其余边不带标签。各阶段没有结果角标。

构图：横向链，默认尺寸。

## recovery-loop：异常恢复闭环

按顺时针循环：监测信号 → 定位原因 → 执行修复 → 复核结果 → 监测信号。第一条边标注「告警」，最后一条边标注「持续监测」。节点当前状态分别为 warn、error、ok、ok。

构图：四节点环，默认尺寸。方向、标签和状态都要清晰。

## service-boundaries：订单与仓储边界

「交易平台」包含「订单服务」与「仓储服务」。订单服务内有「接收订单」和「确认完成」；仓储服务内有「预留库存」和「安排发货」。所有容器标题和四个业务节点都属于主语义。

跨服务关系：接收订单 → 预留库存，标注「预留」；安排发货 → 确认完成，标注「确认」。没有其他箭头或状态角标。

构图：外层平台容器、两个服务容器，960×540 画布。用空间分组表达归属，不额外画出无来源的关系。

## shape-vocabulary：审核分支

四种外形各表示一种语义：「开始」是椭圆起点，进入矩形步骤「提交变更」，由菱形判断「审核通过？」分两路——通过则进入胶囊状态「上线」（结果 ok），驳回则进入胶囊状态「修改」（结果 warn）。两条分支边分别标注「通过」「驳回」，其余两条边不带标签；没有回流，也没有其他角标。

构图：820×450 画布，横向链加一个上出口和一个下出口。菱形外接框 220×130（内接区域才放得下 5 个字），胶囊 120×64；胶囊带角标，宽度按「字宽 + 角标」预留。

## order-sequence：下单时序

参与者为客户端、订单服务、仓储服务。消息按时间顺序编号：

1. 客户端 → 订单服务「1 提交订单」，同步请求（flow）。
2. 订单服务自调用「2 校验订单」（flow）。
3. 订单服务 → 仓储服务「3 预留库存」，同步请求（flow）。
4. 仓储服务 → 订单服务「4 库存结果」，应答（reply）。
5. 订单服务 → 客户端「5 下单结果」，应答（reply）。

构图：时序风格，三位参与者各带一条生命线，默认 720×450 画布；请求与应答按 UML 惯例区分线型与箭头（实线实心 / 虚线开放）。

## ops-architecture：巡检架构

组件与角色：运营人员（user 图标）、定时调度（clock 图标）、任务队列（queue 图标）、巡检服务、运营数据库（database 图标）、外部监控（cloud 图标）。

关系：运营人员 → 巡检服务「手动触发」；定时调度 → 任务队列「定时投递」；任务队列 → 巡检服务「消费」（异步 async）；巡检服务 → 运营数据库「读写」；巡检服务 → 外部监控「上报」。没有状态角标。

构图：巡检服务居中，触发源在左、下游在右，820×450 画布；六个节点带对应图标。

## order-states：订单状态机

状态与迁移：起点（initial 实心圆点，无标签）→ 待支付；待支付 → 已支付「支付成功」（已支付状态 ok）；待支付 → 已取消「超时关闭」（已取消状态 muted）；已支付 → 终点（final 牛眼，无标签）「订单完成」。

构图：默认 720×450 画布，主线横向，取消分支向下。

## order-data-model：订单数据模型

三个实体按标准 ER（Crow's Foot）表达，每个实体是一个 rows 三列表（键标记 / 列名 / 类型）：

- 客户：PK customer_id bigint；name citext；phone citext。
- 订单：PK order_id bigint；FK customer_id bigint；total_amount numeric；status citext。
- 订单明细：PK item_id bigint；FK order_id bigint；quantity integer；unit_price numeric。

关系两条，均为 1:N：客户 → 订单「1:N」（start one 短杠贴客户一侧、kind many 鸦脚贴订单一侧）；订单 → 订单明细「1:N」（同样 start one + kind many）。没有状态角标；compose/aggregate 菱形由 order-class 帧展示，本帧不出现。

构图：默认 720×450 画布，三个实体横排一行、中线对齐，连线用直线（line）；框高按 67 + 20×行数 预算。

## approval-swimlane：审批泳道

三个角色各执一段：提交人、审核人、财务。流程：提交人「提交申请」，交给审核人判断「审核通过？」；通过则进入财务「财务打款」，驳回则回到提交人「退回修改」。边：提交申请 → 审核通过？（无标签）；审核通过？ → 财务打款「通过」；审核通过？ → 退回修改「驳回」。没有状态角标。

构图：泳道泳池（单外框 + 标题带 + 道间分隔线）铺满 820×450 画布，三条竖道从左到右为提交人、审核人、财务——道本身是语义节点；流程自上而下——提交申请在提交人道顶，菱形判断在审核人道，财务打款在财务道中，驳回回到提交人道中的退回修改。跨道连线横向、道内连线纵向，用 line/elbow 让走线横平竖直。

## order-class：订单类图

三个类：Customer（字段 id、name，无方法）；Order（字段 id、总额、状态；方法 提交、取消）；OrderItem（字段 数量、单价，无方法）。关系：Customer → Order「1:N」（kind many，鸦脚朝 Order 一侧）；Order → OrderItem「包含」（start compose，实心菱形贴 Order 一侧）。没有状态角标。

构图：820×450 画布，三个分栏类盒横排一行，中线对齐；框高按 24(标签)+16(分隔)+20×行数 预留。

## conversion-funnel：转化漏斗

四段按顺序缩水：曝光 12000 → 点击 3600 → 注册 900 → 付费 180。转化率 30%/25%/20% 由相邻阶段量级派生，不作为关系边，以注记（notes）呈现在间隙中线右侧。没有状态角标，没有其他箭头。

构图：720×450 画布，四个 trapezoid 垂直居中堆叠，宽度递减（下边缘内缩 12%，宽度按约 0.76 倍递减使上下边缘连续），高 64、间距 44；value 写量级，阶段间不画箭头。

## layered-architecture：分层架构

三层：接入层（Web 网关、API 网关）、服务层（订单服务、仓储服务、巡检服务）、数据层（订单库、缓存，均带 database 图标）。跨层关系自上而下两条：Web 网关 → 订单服务；订单服务 → 订单库。边无标签，没有状态角标。

构图：三个全宽 group（接入层/服务层/数据层）纵向堆叠于 820×450 画布，上层依赖下层；跨层关系用竖直 line，调用方与被调方同一 x 对齐。

## priority-matrix：优先级四象限

四个象限各放一件事：重要紧急（修复线上故障）、重要不紧急（版本规划）、紧急不重要（临时会议）、不重要不紧急（整理文档）。横轴「紧急 →」，纵轴「重要 →」。没有箭头，没有状态角标。

构图：2×2 四个 group 铺满 720×450 画布，中间留十字空隙；轴方向用 notes 标注在空隙与外侧留白中。

## fulfillment-swimlane：履约泳道（复杂流）

五个角色各执一段：客户、订单服务、财务、仓储、物流。流程：客户「提交订单」→ 订单服务判断「库存充足？」；充足则「创建订单」，缺货则退回客户「提交订单」；创建订单 → 财务判断「支付成功？」；成功则仓储「拣货打包」→ 物流「揽收配送」；失败则退回订单服务「创建订单」；最后客户「签收」。

边：提交订单 → 库存充足？（无标签）；库存充足？ → 创建订单「充足」；库存充足？ → 提交订单「缺货」；创建订单 → 支付成功？（无标签）；支付成功？ → 拣货打包「成功」；支付成功？ → 创建订单「失败」；拣货打包 → 揽收配送（无标签）；揽收配送 → 签收（无标签）。没有状态角标。

构图：泳道泳池五条竖道铺满 980×560 画布；两个判断菱形各占一道；两条回流（缺货 3 段、失败 4 段）与签收跨四道的回程都必须横平竖直、末端留直线段给箭头，标签只落在长线段上。

## ecommerce-er：电商数据模型（复杂 ER）

七个实体，各为 rows 三列表（键标记 / 列名 / 类型）：

- 客户：PK id bigint；name citext；phone citext。
- 收货地址：PK id bigint；FK customer_id bigint；receiver citext；detail citext。
- 订单：PK id bigint；FK customer_id bigint；FK address_id bigint；total_amount numeric；status citext。
- 支付单：PK id bigint；FK order_id bigint；amount numeric；method citext。
- 订单明细：PK id bigint；FK order_id bigint；FK product_id bigint；quantity integer；unit_price numeric。
- 商品：PK id bigint；sku citext；name citext；FK category_id bigint。
- 分类：PK id bigint；name citext；FK parent_id bigint。

关系七条，均为 start one + kind many（短杠贴「一」侧、鸦脚贴「多」侧）：客户 → 订单「1:N」；客户 → 收货地址「1:N」；订单 → 订单明细「1:N」；订单 → 支付单「1:N」；商品 → 订单明细「1:N」；分类 → 商品「1:N」；分类 → 分类「父子」（自引用）。没有状态角标。

构图：1010×620 画布，七个实体按依赖分列布居；自引用用实体上方的小环（elbow），跨列长关系沿右侧竖走线。
