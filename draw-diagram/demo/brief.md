# Demo 输入：交付与运营图解

本文件是 demo 的内容来源。图稿中的节点、文案、方向和状态以此为准；它不依赖课程数据或任何项目运行时。

## release-flow：发布流水线

四个阶段按顺序执行：代码提交 → 自动构建 → 变更验收 → 灰度上线。代码提交触发自动构建，第一条边标注「触发」。其余边不带标签。各阶段没有结果角标。

构图：横向链，默认尺寸。

## recovery-loop：异常恢复闭环

按顺时针循环：监测信号 → 定位原因 → 执行修复 → 复核结果 → 监测信号。第一条边标注「告警」，最后一条边标注「持续监测」。节点当前状态分别为 warn、error、ok、ok。

构图：四节点环，默认尺寸。方向、标签和状态都要清晰。

## service-boundaries：订单与仓储边界

「交易平台」包含「订单服务」与「仓储服务」。订单服务内有「接收订单」和「确认完成」；仓储服务内有「预留库存」和「安排发货」。所有容器标题和四个业务节点都属于主语义。

跨服务关系：接收订单 → 预留库存，标注「预留」；安排发货 → 确认完成，标注「确认」。没有其他箭头或状态角标。

构图：外层平台容器、两个服务容器，960×540 画布。用空间分组表达归属，不额外画出无来源的关系。

## shape-vocabulary：审核分支

四种外形各表示一种语义：「开始」是椭圆起点，进入矩形步骤「提交变更」，由菱形判断「审核通过？」分两路——通过则进入胶囊状态「上线」（结果 ok），驳回则进入胶囊状态「修改」（结果 warn）。两条分支边分别标注「通过」「驳回」，其余两条边不带标签；没有回流，也没有其他角标。

构图：820×450 画布，横向链加一个上出口和一个下出口。菱形外接框 220×130（内接区域才放得下 5 个字），胶囊 120×64；胶囊带角标，宽度按「字宽 + 角标」预留。

## order-sequence：下单时序

参与者为客户端、订单服务、仓储服务。消息按时间顺序编号：

1. 客户端 → 订单服务「1 提交订单」，同步请求（flow）。
2. 订单服务自调用「2 校验订单」（flow）。
3. 订单服务 → 仓储服务「3 预留库存」，同步请求（flow）。
4. 仓储服务 → 订单服务「4 库存结果」，应答（reply）。
5. 订单服务 → 客户端「5 下单结果」，应答（reply）。

构图：时序风格，三位参与者各带一条生命线，默认 720×450 画布；请求与应答按 UML 惯例区分线型与箭头（实线实心 / 虚线开放）。

## ops-architecture：巡检架构

组件与角色：运营人员（user 图标）、定时调度（clock 图标）、任务队列（queue 图标）、巡检服务、运营数据库（database 图标）、外部监控（cloud 图标）。

关系：运营人员 → 巡检服务「手动触发」；定时调度 → 任务队列「定时投递」；任务队列 → 巡检服务「消费」（异步 async）；巡检服务 → 运营数据库「读写」；巡检服务 → 外部监控「上报」。没有状态角标。

构图：巡检服务居中，触发源在左、下游在右，820×450 画布；六个节点带对应图标。

## order-states：订单状态机

状态与迁移：起点（initial 实心圆点，无标签）→ 待支付；待支付 → 已支付「支付成功」（已支付状态 ok）；待支付 → 已取消「超时关闭」（已取消状态 muted）；已支付 → 终点（final 牛眼，无标签）「订单完成」。

构图：默认 720×450 画布，主线横向，取消分支向下。

## order-data-model：订单数据模型

实体与关系：客户 → 订单「1:N」（kind many，鸦脚朝订单一侧）；订单 → 订单明细「包含」（start compose，实心菱形贴订单一侧）；促销方案 → 商品「引用」（start aggregate，空心菱形贴促销方案一侧）。

构图：默认 720×450 画布，上下两行横排。
